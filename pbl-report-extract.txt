2. Introduction
A web application is software that runs on a web server and is used through a web browser. Unlike 
a static website that only shows fixed pages, a web application accepts input from users, stores data 
in a database and shows each user information that matches their role. Modern web applications are 
usually split into a frontend (what the user sees), a backend (the server logic and API) and a 
database (where data is stored permanently).
The United Nations Sustainable Development Goals (SDGs) are 17 global goals for 2030. SDG 2 
– Zero Hunger aims to end hunger, and SDG 12 – Responsible Consumption and Production 
includes target 12.3, which aims to halve food waste by 2030. In India, hotels, hostels, caterers and 
wedding halls throw away large amounts of good cooked food every day, while NGOs and food 
banks nearby struggle to collect enough food for the people they serve.
The real problem is the last mile: cooked food stays fresh for only a few hours, and donors and 
NGOs have no quick, reliable way to find each other within that time. Phone calls and WhatsApp 
groups are slow, messages get lost, two NGOs may travel for the same food, and nobody can 
measure how much food was actually saved.
In this project a web application named FoodBridge is designed and developed using the MERN 
stack. A donor lists surplus food with its quantity, pickup address and expiry time. Nearby NGOs 
see the listing, one NGO claims it, collects it and marks it picked up. The home page shows live 
impact numbers: meals served, kilograms of food rescued and CO₂ emissions avoided.
Need of the project: faster matching of surplus food with NGOs, no double pickups, less food 
going to landfill, a record of every donation, and measurable SDG impact that donors and NGOs 
can see.

3.2 Problem Statement
Restaurants, hostels and caterers regularly have surplus cooked food that is still safe to eat, but it is 
thrown away because there is no fast way to inform nearby NGOs before it spoils. NGOs, on the 
other hand, do not know where food is available, and when information is shared informally two 
NGOs may go for the same food while other food expires. There is also no record of how much 
food is rescued. A web application is required that lets donors list surplus food quickly, lets NGOs 
find and claim it without conflicts, tracks every donation from listing to pickup, and shows the 
social and environmental impact in real time.
3.3 Objectives
1. To design and develop a full-stack web application using React, Node.js, Express.js and 
MongoDB.

authentication.

4. Proposed System / System Design
4.1 System Architecture
FoodBridge follows a three-tier client–server architecture (Figure 1). The React application 
runs in the browser and sends HTTP requests in JSON format. The Express server checks the 
request through a chain of middleware, runs the business logic in a controller, and reads or writes 
data in MongoDB through Mongoose. The server then sends a JSON response, and React updates 
only the parts of the page that changed.

4.6 Working of the System
Every donation moves through a fixed life-cycle (Figure 2). Only food that reaches the picked up 
state is counted in the impact numbers; food that reaches expired is counted as wasted.

Figure 2: Donation status life-cycle
1. The donor logs in. The server checks the password with bcrypt and returns a signed JWT, 
which React saves in localStorage.
2. The donor fills the donation form. React sends POST /api/donations with the token; the 
protect middleware verifies the token and authorize('donor') checks the role.
3. Mongoose validates the data against the schema and saves it in the donations collection 
with status available.
4. An NGO opens Find Food. React calls GET /api/donations?status=available and 
shows each listing as a card.
5. The NGO clicks Claim. The server runs findOneAndUpdate with the condition status = 
available, so if two NGOs click together only one succeeds and the other receives 409 
Conflict.
6. After collecting the food, the NGO clicks Mark picked up. The status changes to picked_up 
and the impact numbers increase.
7.
GET /api/stats uses MongoDB aggregation ($match, $group, $sort) to calculate meals 
(kg ÷ 0.4) and CO₂e avoided (kg × 2.5, based on FAO estimates).
4.7 Security Features
•
Passwords are hashed with bcrypt (salt and 10 rounds) before saving; plain passwords are 
never stored.
•
JWT authentication: protected routes return 401 Unauthorized without a valid token.
•
Role-based authorization on the server: wrong role returns 403 Forbidden, even if the 
browser is modified.
•
The donor ID is taken from the token, not from the request body, and only whitelisted fields 
can be updated.
•
Secrets (database URL, JWT secret) are kept in a .env file that is excluded from Git.
•
A central error handler converts validation errors to 400, duplicate emails to 409 and 
unknown routes to 404.

6. Conclusion and Future Scope
FoodBridge solves a real social problem with a complete web application. Donors can list surplus 
food in under a minute, NGOs can find and claim it without conflicts, and every donation is tracked 
from listing to pickup. The project uses all the main parts of web application development: HTML 
and CSS for structure and layout, JavaScript for logic, React for the user interface, Node.js and 
Express for the REST API, MongoDB for storage, and security with bcrypt and JWT. The live 
impact dashboard connects the work directly to SDG 2 and SDG 12.
Future scope:
•
Map view with distance-based sorting using geolocation.
•
SMS or WhatsApp alerts to nearby NGOs when new food is listed.
•
Photo upload of food and a food-safety checklist for donors.
•
Volunteer driver role for pickup and delivery.
•
Progressive Web App (PWA) and monthly impact reports for donors.
